# 报错先对发版：事故排查出时间线

- **适合**：线上一报警就想回滚，又经常回滚完报错还在的人
- **详细教程**：[grokguide.si/tutorials/incident-timeline](https://grokguide.si/tutorials/incident-timeline)

## 场景

报错一来，Bot 在云电脑上把每种报错第一次出现的时刻和每次发版的时刻排成时间线，分出这次发版引入的、早就有的老问题和跟发版对不上的外部问题，写成草稿。回滚和修复都等你说。

## 准备

- 一份报错记录（时间、报错指纹、报错信息、所在文件），可以从报错平台导出
- 能读发版标签的 git 仓库

## 步骤

1. 报错记录不存在或为空，直接报失败，不沿用上次结果。
2. 同一种报错归一组，记第一次、最后一次和总次数。
3. 列出每次发版的时刻、提交号和改动文件。
4. 每种报错对上它首次出现前的最近一次发版：同文件、两小时内出现的写成假设；比改这个文件的发版还早的算老问题；文件没改过的先查外部依赖。
5. 写 timeline.md，结论念一遍，不动生产。

## 提示词

```text
线上有报错时，帮我先排一条时间线，不要先猜原因：
1. 读我给你的报错记录。读不到或是空的，直接告诉我“这次没查成”，不要用上次的结果。
2. 同一种报错归成一组，列出第一次出现、最后一次出现、总次数，时间用北京时间。
3. 读仓库的发版标签，列出每次发版的时刻、提交号和改了哪些文件。
4. 每种报错对上它第一次出现之前的最近一次发版。同一文件、发版后两小时内出现的，写成“假设：这个版本引入”；比发版还早的写“老问题”；文件没改过的写“先查外部依赖”。
5. 写成 timeline.md 发给我，并念一遍结论。不要回滚、不要改配置、不要重启任何服务，等我说了再动。
```

## 产出

timeline.md（时间线、假设、建议草稿）和 timeline.json。

## 注意事项

- “谁引入的”永远是假设，时间和提交号才是事实。
- 回滚、改配置、重启服务都要你批准。
- 做成 Sentry 或 PagerDuty 触发的 Routine 前，先手动跑通一次并存成 skill。
- 所有 Bot 共用一台云电脑和登录，给排查 Bot 的权限按事来收。

## 小伟点评

虚构 4 次发版、221 条报错实跑两遍：只怪最近一次发版，4 种报错错了 3 种；对上首次出现后，折扣码报错找回到早 6 个多小时的那次发版，数据缺失时只报失败。
